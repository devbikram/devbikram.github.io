ProductionDisney Streaming

Agentic AI Marketing Automation

Producing, translating and approving marketing content took heavy manual effort and slow review cycles. A multi-agent GenAI workflow that drafts and translates marketing content, has a critic agent review it, and routes it to people for approval, with guardrails and brand checks built in.

60–70%less manual effort

better first-pass approvals

  • LangGraph
  • OpenAI
  • pgvector
  • Cohere Rerank
  • NeMo Guardrails
  • React

How it was built

Challenge. Every campaign needed English copy, creative assets, translations for many regions and languages, and a rendered preview, each signed off by a different person. Done by hand across tools and email, it was slow, drafts went back for repeated rounds, and producing final JPG and PDF files for every region and language was a separate manual job.

My role

  • Led the solution architecture and technical design as Technical Lead / Associate Technical Architect.
  • Modelled the campaign lifecycle as a LangGraph state machine on Amazon EKS: campaign created, AI copy in English, copy approval, image upload, AI translation per locale, linguist review, AI HTML preview, preview approval and delivery. Redis checkpoints pause the graph at every human step.
  • Built the AI agents on fine-tuned OpenAI models: a copywriter, a critic that checks quality and brand fit before anyone reviews, a translator, and a layout agent that generates HTML and JavaScript previews. Brand context comes from pgvector retrieval with Cohere Rerank.
  • Designed the guardrail layer with NeMo Guardrails for risky prompts, PII exposure and output filtering.
  • Built the review flow: linguists approve, edit or reject each translation, and marketers approve a preview, reject it or ask for another layout. Previews download as JPG or PDF or go out by email as an expiring secure link.
  • Designed the bulk export job: a reviewer picks regions and languages, SQS queues one render job per asset, headless Chromium workers on EKS produce the JPG and PDF files, and the bundle lands in S3 with an email link.
  • Integrated Salesforce for campaign briefs, Braze for sending approved creatives and Snowflake for analytics. Campaign data lives in RDS PostgreSQL and assets in S3, encrypted with KMS, with events on SNS, email through SES and handlers on Lambda.
  • Set up delivery through GitHub, Jenkins, Docker and Kubernetes, with CloudWatch logs, metrics and alarms.

Key decisions

  • Graph orchestration with human checkpoints: LangGraph makes each agent step, human approval and retry explicit. Checkpoints in Redis let a campaign wait for a reviewer without holding compute, then resume where it stopped.
  • Critic before human: An automated review pass catches common problems early, which is where the first-pass approval gains come from.
  • Rejections loop back with feedback: A rejection returns the campaign to the previous AI step with the reviewer's notes, so the next draft addresses them instead of starting over.
  • Queue-based fan-out: Translation and rendering run as one SQS job per locale or asset, so large campaigns scale out on EKS and a single failure is retried on its own.
  • One renderer for preview and export: The bulk job uses the same HTML renderer as the live preview, so the files people download match what they approved.
  • Guardrails as a separate layer: Keeping input and output filters outside the agents lets them be updated without changing the workflow.

Results

  • 60–70% reduction in manual effort.
  • Approximately 50% faster content processing cycle.
  • 20–25% improvement in first-pass approvals.

Enterprise RAG Knowledge Assistant

People couldn't reliably find answers buried across large internal document collections. As an AI Engineer, I built an enterprise Retrieval Augmented Generation (RAG) knowledge assistant using Python, FastAPI, LangGraph, LangChain, Chainlit, Docling, and PostgreSQL/pgvector. Implemented document parsing, chunking, hybrid BM25 + vector search, reranking, LLM integration, AI guardrails, and RAGAS evaluation.

How it was built

Challenge. People couldn't reliably find answers buried across large internal document collections. Plain vector search returned loosely related passages, answers were slow, inference costs rose with usage, and the assistant had to respect who is allowed to see which documents.

My role

  • Designed the end-to-end retrieval architecture as architect and lead engineer.
  • Built ingestion with Docling: documents are parsed with their structure intact, then split with context-aware chunking and embedded into PostgreSQL with pgvector.
  • Implemented hybrid retrieval that merges BM25 keyword search with pgvector semantic search, followed by a reranking pass so only the most relevant context reaches the model.
  • Orchestrated the answer flow with LangGraph and LangChain: retrieve, rerank, route the query to a model that fits its complexity, then generate a grounded answer behind AI guardrails.
  • Built the FastAPI service and the Chainlit chat interface, with Redis caching repeated queries and embeddings.
  • Set up RAGAS evaluation as a pipeline so every retrieval change is scored before release, and tuned latency and cost against those scores.

RAG retrieval pipeline

RAG retrieval pipeline

Key decisions

  • Hybrid over pure vector search: Keyword matching catches exact terms, IDs and acronyms that embeddings miss.
  • Rerank before generation: A reranking pass keeps the context window small and relevant, which improves precision and cuts tokens.
  • Structure-aware parsing: Parsing with Docling keeps headings, tables and sections together, so chunks carry their meaning.
  • Evaluation as a pipeline: RAGAS scores make retrieval changes measurable, so precision gains can be shown rather than claimed.
  • Routing and caching for cost: Not every query needs the largest model, and many repeat. Together these drove the cost reduction.

Results

  • Approximately 35% improvement in retrieval precision.
  • 40% faster query resolution.
  • P95 response latency reduced from 3.2s to 1.9s.
  • 25–30% reduction in inference cost.

Enterprise AI Interview Platform

Screening interviews take a lot of interviewer time and are hard to keep consistent across candidates. Designed an enterprise Agentic AI interview solution integrating Azure OpenAI, LangGraph, Python, FastAPI, LiveKit, ElevenLabs, and HeyGen. Architected real-time AI interviews with interactive voice/video, adaptive questioning, AI-powered evaluation, session recovery, and human-reviewed proctoring. Defined Azure cloud architecture, security controls, scalable deployment, technical specifications, and capacity planning.

  • Azure OpenAI
  • LangGraph
  • FastAPI
  • LiveKit
  • ElevenLabs
  • HeyGen
  • PostgreSQL
  • Azure
How it was built

Challenge. Screening interviews take a lot of interviewer time and are hard to keep consistent across candidates. Running them with AI means holding hundreds of live voice and video sessions at once, keeping each one isolated, recovering cleanly when a connection drops, and producing an evaluation that a person can trust and review.

My role

  • Designed the solution architecture, Azure cloud architecture, security controls, technical specifications and capacity planning as solution architect.
  • Sized the platform for 300 concurrent candidates, each running in an isolated LiveKit agent session, behind an Application Gateway with WAF and a load balancer for WebRTC traffic.
  • Designed the live orchestration: a FastAPI backend, a LiveKit dispatcher that assigns each candidate to an agent worker, and session recovery so an interview resumes after a disconnect.
  • Defined the agent harness with LangGraph: a scanning agent, an interview agent that adapts questions to the role and previous answers, an async start tool and recruitment agents.
  • Connected the real-time AI services: speech-to-text, Azure OpenAI GPT for the interviewer, ElevenLabs text-to-speech and a HeyGen live avatar.
  • Designed media and recording: the LiveKit SFU routes media, track egress captures each session to blob storage, and a post-processing pipeline fetches, composes, validates and uploads the final video, then cleans up.
  • Designed the data and event layer: Redis for live session state, PostgreSQL for dialogue and reports, and Azure Service Bus events for completed or failed interviews.
  • Designed AI evaluation with human review: logs are scored against a rubric by GPT, saved as a report and sent to the recruiter workbench, Oracle Fusion HCM and governance and audit systems.

Key decisions

  • One isolated worker per session: Each candidate gets their own LiveKit agent worker, so a slow or failed session never affects another and capacity scales by adding workers.
  • Stateful graph with recovery: Modelling the interview as a LangGraph flow with state in Redis lets a session resume where it stopped after a disconnect.
  • Record raw tracks, compose later: Capturing each track during the call and composing the video afterwards keeps the live path fast and makes recording failures recoverable.
  • Event-driven hand-off: Service Bus events for completed or failed interviews decouple evaluation and HR integrations from the live system.
  • Human review as a required step: AI evaluation supports reviewers rather than replacing them.

AI-Powered Newspaper Block Detection

Marking out each article block on scanned newspaper pages was slow, repetitive manual work. As an AI Engineer, I trained a custom YOLO26 object detection model using Roboflow to identify newspaper content blocks for OdishaPOST ePaper. Developed a computer vision solution to detect news articles, advertisements, images, headlines, and page elements from complex newspaper layouts. The trained model achieved 79.5% mAP@50, 80.7% precision, 83.3% recall, and 81.0% F1 score on Roboflow's test set.

How it was built

Challenge. Newspaper layouts vary widely: multi-column articles, ads, photos, headlines and captions sit side by side. Someone had to mark the boundary of every block on every page by hand before an ePaper edition could be processed.

My role

  • Prepared the dataset and annotated newspaper pages in Roboflow, labelling news articles, advertisements, images, headlines and other page elements.
  • Trained and evaluated a custom YOLO26 object-detection model on that dataset.
  • Measured the model on Roboflow's held-out test set before using it in the workflow.
  • Wrapped inference in a FastAPI service that takes a page image and returns the detected blocks for the OdishaPOST ePaper workflow.

Key decisions

  • Object detection over rule-based layout parsing: A trained detector copes with layout variety better than hand-written rules.
  • Separate classes for page elements: Labelling articles, ads, images and headlines separately lets the workflow treat each kind of block differently.
  • Measure on a held-out test set: Reporting precision, recall and F1 on unseen pages shows how the model will behave on new editions.

Results

  • 79.5% mAP@50, 80.7% precision, 83.3% recall and 81.0% F1 on the Roboflow test set.
  • Approximately 70% less manual block-identification effort, as reported in the owner’s brief.

Dharitri: High-Traffic News Platform

A busy regional news site had to stay fast and online through traffic spikes on 1M+ daily visitors. Production AWS architecture for a high-traffic publishing platform: caching, CDN delivery, database tuning, security configuration and deployment automation.

daily visitors supported
1M+daily visitors supported
  • AWS EC2
  • ALB
  • CloudFront
  • Redis
  • MySQL / MariaDB
  • PHP
  • WordPress
  • Nginx
How it was built

Challenge. Dharitri.com serves 1M+ daily readers on web, mobile and AMP, and breaking stories send sudden traffic surges. The old hosting had persistent uptime problems and could not scale without constant manual work.

My role

  • Moved the WordPress platform from legacy hosting onto AWS and managed the infrastructure.
  • Put the edge in front: Route 53 for DNS, CloudFront for edge caching and HTTPS with ACM certificates, and AWS WAF and Shield for firewall rules and DDoS protection.
  • Ran the application tier as nginx and PHP-FPM WordPress servers on EC2 in an Auto Scaling group behind an Application Load Balancer, in private subnets inside a VPC, adding servers automatically when breaking news spikes.
  • Tuned the database on Amazon RDS (MySQL) and added ElastiCache Redis as the WordPress object cache, so most reads never reach the database.
  • Moved images and media to Amazon S3 served through CloudFront, with EFS keeping shared wp-content in sync across servers.
  • Set up CloudWatch metrics, logs and alarms, AWS Backup snapshots for the database and servers, and automated deployments.

Key decisions

  • Cache in layers: Edge, object and database caching each take load off the layer behind them, so spikes rarely reach the database.
  • Stateless servers in an Auto Scaling group: With media in S3 and shared files on EFS, any server can be added or replaced, so capacity follows traffic automatically.
  • Media off the web servers: Serving images from S3 through CloudFront removes the heaviest requests from the application tier.
  • Security at the edge: WAF and Shield stop bad traffic before it reaches the servers, and private subnets keep the application and data tiers off the public internet.

Results

  • Supports a platform serving 1M+ daily visitors.
  • Resolved persistent uptime issues after the AWS migration.
